# ТЗ на MVP сервиса заявок в общежитии

Реализуй работающий веб-сервис. Студенты сообщают о неисправностях в комнатах, специалисты берут заявки в работу, администратор управляет справочными данными и просматривает заявки.

## Стек и результат

- Монолит на Python и FastAPI. Интерфейс на HTML и CSS с серверными шаблонами Jinja2.
- PostgreSQL, SQLAlchemy как ORM, Alembic для миграций. Правила работы с заявками и проверки прав вынеси из маршрутов в сервисы. Используй классы для моделей и сервисов.
- Подготовь исходный код, файл зависимостей, `.env.example`, миграции, сидер и `README.md` с командами установки, настройки БД, запуска миграций, сидера и сервера. Перед сдачей проверь критерии приёмки.

## Вход и роли

- Три роли — студент, специалист, администратор. После входа пользователь попадает в кабинет своей роли. В меню доступны разделы, соответствующие его правам. В каждом кабинете есть выход из аккаунта.
- Для MVP используй вход по логину и паролю. Сидер создаёт сразу активные аккаунты студентов с именами и адресами комнат. Добавь демонстрационные аккаунты двух студентов, администратора и по одному специалисту каждой специальности. При повторном запуске сидер добавляет только отсутствующие записи. Укажи в README, как войти под демонстрационными аккаунтами.
- Сидер служит источником данных студентов для MVP. Интеграция с основным сервисом относится к следующему этапу.

## Студент

В кабинете студент видит список своих заявок, включая выполненные и отменённые, и может открыть каждую карточку. В списке отображаются номер заявки, комната, специальность, статус и дата создания. Новые заявки отображаются выше старых.

### Поля заявки

| Поле | Правило |
| --- | --- |
| Общежитие | Обязательно. По умолчанию из профиля, можно изменить. |
| Номер комнаты | Обязательно. По умолчанию из профиля, можно указать другой номер, например `302` или `502`. Хранить как строку. |
| Блок | Необязательно. Если указан в профиле, подставляется автоматически. Можно изменить или очистить. |
| Специальность | Обязательно. Плотник, электрик или сантехник. |
| Описание | Обязательно. Можно ввести вручную или заполнить из пресета выбранной специальности и затем отредактировать. |
| Фото | Необязательно. Для MVP одно фото JPEG или PNG размером до 5 МиБ. |

При отправке сохраняй адрес в самой заявке. Изменения адреса применяются только к заявке. Успешная отправка открывает карточку с номером и статусом заявки. Карточка также показывает описание, фото и адрес.

Студент может изменить поля своей новой заявки, включая замену или удаление фото, либо отменить её. После взятия заявки специалистом студент может только просматривать её.

## Специалист

- Специальность закреплена за аккаунтом сотрудника. В очереди видны только новые заявки его специальности. Сортировка по возрастанию даты создания, при равных датах — по номеру заявки. Фильтры по общежитию и диапазону дат создания.
- Из карточки новой заявки специалист может взять её в работу. Заявка закрепляется за ним и исчезает из общей очереди.
- В разделе «Мои заявки» специалист видит взятые им заявки, включая выполненные. Фильтры по статусу, общежитию и диапазону дат создания. Специалист может отметить свою заявку в работе выполненной.

## Администратор

- Просматривает список и карточки всех заявок. Фильтры по исполнителю, специальности, статусу, общежитию и диапазону дат создания. Выбранные фильтры применяются одновременно.
- Создаёт и редактирует аккаунты специалистов, включая назначение специальности. Если специальность сотрудника меняется, ранее взятые им заявки остаются в разделе «Мои заявки».
- Создаёт, редактирует и отключает пресеты. У пресета есть название, текст описания и специальность. Студенту показываются активные пресеты для выбранной специальности. Замена текста пресета влияет только на его последующее использование.

## Статусы и переходы

| Исходный статус | Действие | Кто выполняет | Новый статус |
| --- | --- | --- | --- |
| — | Создать | Студент | Новая |
| Новая | Изменить | Автор заявки | Новая |
| Новая | Отменить | Автор заявки | Отменена |
| Новая | Взять в работу | Специалист нужной специальности | В работе |
| В работе | Завершить | Закреплённый специалист | Выполнена |

Проверяй допустимость действия для текущего статуса атомарно с изменением данных, например условным обновлением или блокировкой строки на время транзакции. Сохраняй статус и назначенного исполнителя одной транзакцией. При попытке изменить заявку из устаревшей карточки покажи сообщение о том, что она уже изменилась. Отменённые заявки сохраняются в истории.

## Данные и защита

- Минимальные сущности — пользователь, заявка, пресет и вложение. В профиле студента храни адрес, у специалиста — специальность. В заявке храни уникальный номер, автора, адрес, специальность, описание, статус, исполнителя при наличии, даты создания и обновления, взятия и выполнения.
- Проверяй право доступа на сервере для списков, карточек, действий и выдачи фото, включая прямые ссылки. Студенту доступны только его заявки. Специалисту доступны карточки из его текущей очереди и заявки, закреплённые за ним.
- Храни пароли в виде стойких хешей. Для cookie сессии используй `HttpOnly`, `SameSite` и `Secure` при HTTPS. Защити изменяющие формы от CSRF. Секреты приложения и параметры БД передавай через окружение.
- Проверяй размер и фактический формат фото на сервере. Храни фото отдельно от записи заявки, например в таблице вложений, и отдавай через маршрут с проверкой прав. При ошибке загрузки сообщай причину и сохраняй введённые поля формы.
- Добавь раздел «Контакты» с контактом разработчика. Значение задаётся в конфигурации приложения и описано в README.

## Критерии приёмки

1. По README можно развернуть сервис на пустой БД. Сразу после запуска сидера студент входит и видит предзаполненный адрес в форме заявки.
2. Студент создаёт заявку с пресетом, изменённым номером комнаты и фото. Карточка показывает введённый адрес, профиль показывает адрес из сидера.
3. Второй студент не может получить чужую заявку или фото по прямому URL. Специалист другой специальности не видит эту заявку в своей очереди и не может взять её.
4. Новые заявки показываются специалисту от старых к новым. Из двух одновременных попыток взять одну заявку успешна только одна.
5. Новую заявку можно изменить или отменить. Если специалист уже взял её, сервер отклоняет изменение или отмену, даже когда форма была открыта раньше. Отменённая заявка видна автору в истории.
6. Закреплённый специалист завершает заявку, и студент видит статус «Выполнена». Администратор находит её через фильтры. Новый активный пресет появляется в форме после выбора соответствующей специальности.
